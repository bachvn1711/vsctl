# vssctl Handbook

This handbook documents the commands that are implemented by the current
`vssctl` source tree. Run all examples from the repository root unless a
section says otherwise.

## 1. What vssctl Does

`vssctl` manages a custom Vehicle Signal Specification (VSS) catalog and can:

1. add, list, search, and remove custom signals;
2. validate the catalog;
3. generate VSS JSON release files;
4. build a custom Eclipse KUKSA Databroker image with Docker or Podman;
5. publish the image to GitHub Container Registry (GHCR);
6. browse the catalog in a terminal or read-only web dashboard.

The usual workflow is:

```text
signal add -> validate -> generate -> build -> run -> test -> publish
```

## 2. Repository Layout

```text
workspace/
|-- catalog/
|   |-- signals-base.yaml       # Baseline branch catalog
|   `-- signals-custom.yaml     # Custom branches and signals
|-- templates/
|   |-- spec/                   # VSS source files, units, and quantities
|   `-- vss-core/               # Baseline VSS JSON releases
|-- generated/
|   |-- company.vspec           # Generated custom overlay
|   |-- merged/                 # Temporary merged compiler input
|   `-- json_tree/
|       `-- vss_release_*.json  # Generated release JSON files
`-- databroker/
    `-- kuksa-databroker/       # KUKSA Databroker source repository
```

Important facts:

- `signals-custom.yaml` is the file changed by `vssctl signal add` and remove
  commands.
- `signals-base.yaml` is generated by `vssctl signal update`.
- Generated release files are written under
  `workspace/generated/json_tree/`, not directly under
  `workspace/generated/`.
- Generated files may be ignored by Git. They can still be inspected locally
  with normal file tools or with `git status --ignored`.

## 3. Installation

### Prerequisites

- Python 3.10 or newer;
- Git;
- Podman or Docker for image build and publish commands;
- the KUKSA Databroker source tree for `vssctl build`.

### Windows PowerShell

Create a clean virtual environment inside the repository:

```powershell
python -m venv .venv_win
.\.venv_win\Scripts\Activate.ps1
python -m pip install --upgrade pip
python -m pip install -r requirements.txt
python -m pip install -e .
```

For development and tests:

```powershell
python -m pip install -r requirements-dev.txt
python -m pytest
```

If PowerShell blocks activation for the current terminal session:

```powershell
Set-ExecutionPolicy -Scope Process -ExecutionPolicy Bypass
.\.venv_win\Scripts\Activate.ps1
```

To keep the environment outside the repository:

```powershell
python -m venv "$env:LOCALAPPDATA\vssctl-venv"
& "$env:LOCALAPPDATA\vssctl-venv\Scripts\Activate.ps1"
python -m pip install --upgrade pip
python -m pip install -r requirements.txt
python -m pip install -e .
```

### Linux or macOS

```bash
python3 -m venv .venv
source .venv/bin/activate
python -m pip install --upgrade pip
python -m pip install -r requirements.txt
python -m pip install -e .
```

For development and tests:

```bash
python -m pip install -r requirements-dev.txt
python -m pytest
```

### Verify the installation

```powershell
vssctl --help
vspec --help
python -m pip check
```

`vss-tools` from `requirements.txt` provides the `vspec` compiler used by
`vssctl generate`. `textual` is required by `vssctl browse`, and `flask` is
required by `vssctl dashboard`.

The current `vssctl doctor` implementation prints the platform and `OK`. It
does not yet verify `vspec`, Flask, Textual, Podman/Docker, or workspace paths,
so use the explicit checks above when troubleshooting an installation.

## 4. Prepare Podman and KUKSA Databroker

On Windows, initialize and start the Podman virtual machine if necessary:

```powershell
podman machine init
podman machine start
podman info
```

If `podman machine init` says a machine already exists, only run the start and
info commands.

`vssctl build` accepts either of these Databroker layouts:

```text
workspace/databroker/Cargo.toml
workspace/databroker/kuksa-databroker/Cargo.toml
```

Clone KUKSA when the directory is absent:

```powershell
git clone https://github.com/eclipse-kuksa/kuksa-databroker.git workspace\databroker\kuksa-databroker
```

Verify the expected build root:

```powershell
Test-Path workspace\databroker\kuksa-databroker\Cargo.toml
podman ps
```

Both commands must succeed before a Podman build.

## 5. Global CLI Syntax

```text
vssctl [GLOBAL OPTIONS] COMMAND [COMMAND OPTIONS]
```

Global options must be placed before the command:

| Option | Meaning |
|---|---|
| `--config <file>` | Load a custom `.vssctl.yaml` file. |
| `--verbose`, `-v` | Enable verbose mode. |
| `--quiet`, `-q` | Enable quiet mode. |
| `--install-completion` | Install completion for the current shell. |
| `--show-completion` | Print completion for the current shell. |
| `--help` | Show help. |

Examples:

```powershell
vssctl --help
vssctl --verbose validate
vssctl --config .\.vssctl.yaml generate --version 6.0
vssctl signal --help
vssctl build --help
```

There is no top-level `vssctl list` command. Use `vssctl signal list`.

## 6. Complete Command Reference

### `vssctl doctor`

Print basic platform information and an `OK` status.

```powershell
vssctl doctor
```

See the installation verification commands in section 3 for a complete
environment check.

### `vssctl signal list`

Print baseline and custom signal paths. The custom list combines catalog
entries with custom paths found in generated output.

```powershell
vssctl signal list
```

### `vssctl signal add`

Interactively add one branch or signal to `signals-custom.yaml`.

```powershell
vssctl signal add
```

For a branch, answer these prompts:

```text
Node type (signal/branch): branch
Parent: Vehicle.ADAS
Name: DriverMonitoring
Description: Driver monitoring branch
```

For a signal:

```text
Node type (signal/branch): signal
Parent: Vehicle.ADAS.DriverMonitoring
Name: AttentionLevel
Description: Estimated driver attention level
Datatype: uint8
Unit: percent
```

The interactive command currently asks only for node type, parent, name,
description, datatype, and unit. To set `writable`, `minimum`, or `maximum`, edit
the new entry in `workspace/catalog/signals-custom.yaml`:

```yaml
- parent: Vehicle.ADAS.DriverMonitoring
  name: AttentionLevel
  datatype: uint8
  description: Estimated driver attention level
  unit: percent
  writable: false
  minimum: 0
  maximum: 100
```

Use VSS unit identifiers such as `percent` and `Celsius`; display symbols such
as `%` and `°C` are not valid compiler unit names.

### `vssctl signal search`

Search custom signal names, case-insensitively. The search currently matches
the `name` field, not the complete parent path or description.

```powershell
vssctl signal search Speed
vssctl signal search attention
```

### `vssctl signal remove`

Remove one custom signal or a complete custom branch. Removing a branch also
removes all custom children below it.

```powershell
vssctl signal remove Vehicle.ADAS.DriverMonitoring.AttentionLevel
vssctl signal remove Vehicle.ADAS.DriverMonitoring
```

Remove every custom entry:

```powershell
vssctl signal remove --all
```

`-a` is an alias for `--all`.

The top-level `vssctl remove` command is an alias with the same syntax:

```powershell
vssctl remove Vehicle.ADAS.DriverMonitoring.AttentionLevel
vssctl remove --all
```

### `vssctl signal update`

Read a baseline release JSON and regenerate `signals-base.yaml` with its VSS
branches.

```powershell
vssctl signal update
vssctl signal update --version 6.0
vssctl signal update -v 6.0
```

The default version is `6.0`. The matching input file must exist as
`workspace/templates/vss-core/vss_release_<version>.json`.

### `vssctl validate`

Validate entries in `signals-custom.yaml` for duplicate paths, names,
datatypes, parent branches, descriptions, and units.

```powershell
vssctl validate
```

Always validate before generation. A successful run ends with output similar
to:

```text
Success: Catalog is valid. Checked 6 signals.
```

### `vssctl generate`

Generate `company.vspec`, prepare the merged VSS compiler input, compile a VSS
release, and synchronize custom signals into supported legacy JSON files.

Generate one version:

```powershell
vssctl generate --version 6.0
vssctl generate -v 6.0
```

Generate all supported versions:

```powershell
vssctl generate
```

The release output is:

```text
workspace/generated/json_tree/vss_release_<version>.json
```

Check generated files in PowerShell:

```powershell
Get-ChildItem workspace\generated\json_tree\vss_release_*.json
Get-Content workspace\generated\company.vspec
```

### `vssctl build`

Build a KUKSA Databroker image containing a generated VSS JSON file.

| Option | Alias | Default / behavior |
|---|---|---|
| `--vss-file <file>` | `-f` | Highest generated release version found. |
| `--tag <tag>` | `-t` | `kuksa-databroker:vss-<version>`. |
| `--engine <auto|podman|docker>` | | `auto`, preferring a running Podman. |
| `--databroker-dir <dir>` | | Config value or `workspace/databroker`. |
| `--no-cache` | | Disable the container build cache. |
| `--publish` | `-p` | Publish after a successful build. |
| `--token <PAT>` | | GHCR token used with `--publish`. |
| `--username <name>` | | `bachvn1711`. |
| `--remote-tag <tag-or-URI>` | | Remote tag used with `--publish`. |
| `--skip-login` | | Reuse an existing registry login. |

Recommended explicit Podman command:

```powershell
vssctl build `
  --vss-file workspace\generated\json_tree\vss_release_6.0.json `
  --tag localhost/kuksa-databroker:vss-6.0-custom `
  --engine podman
```

Let `vssctl` select the latest generated JSON and default tag:

```powershell
vssctl build --engine podman
```

Use a KUKSA checkout in another directory:

```powershell
vssctl build `
  -f workspace\generated\json_tree\vss_release_6.0.json `
  -t localhost/kuksa-databroker:vss-6.0-custom `
  --engine podman `
  --databroker-dir C:\src\kuksa-databroker
```

Verify the local image:

```powershell
podman images
podman image inspect localhost/kuksa-databroker:vss-6.0-custom
```

Using the `localhost/` prefix is recommended with Podman. Without it, Podman
may treat the name as unqualified and try to pull it from Docker Hub when the
local image does not exist.

### `vssctl publish`

Tag and push an existing local image to GHCR.

| Option | Alias | Default / behavior |
|---|---|---|
| `--image <tag>` | `-i` | Inferred as `kuksa-databroker:vss-<latest>`. |
| `--remote-tag <tag-or-URI>` | `-t` | Local tag suffix. |
| `--token <PAT>` | | `GHCR_TOKEN`, then `CR_PAT`, if omitted. |
| `--username <name>` | | `bachvn1711`. |
| `--engine <auto|podman|docker>` | | `auto`. |
| `--skip-login` | | Skip registry login and use the existing session. |

PowerShell example using an environment variable, which avoids putting the
token directly in shell history:

```powershell
$env:GHCR_TOKEN = "YOUR_GITHUB_PAT"
vssctl publish `
  --image localhost/kuksa-databroker:vss-6.0-custom `
  --remote-tag vss-6.0-custom `
  --username YOUR_GITHUB_USERNAME `
  --engine podman
Remove-Item Env:GHCR_TOKEN
```

If already authenticated:

```powershell
vssctl publish `
  -i localhost/kuksa-databroker:vss-6.0-custom `
  -t ghcr.io/YOUR_GITHUB_USERNAME/databroker:vss-6.0-custom `
  --username YOUR_GITHUB_USERNAME `
  --engine podman `
  --skip-login
```

The token needs permission to write packages.

### `vssctl pipeline`

Run `validate -> generate -> build`, optionally followed by publish.

| Option | Alias | Default |
|---|---|---|
| `--version <version>` | | `6.0` |
| `--vss-file <file>` | `-f` | Latest generated file after generation |
| `--tag <tag>` | `-t` | Derived from VSS version |
| `--engine <auto|podman|docker>` | | `auto` |
| `--databroker-dir <dir>` | | `workspace/databroker` |
| `--no-cache` | | false |
| `--publish` | `-p` | false |
| `--token <PAT>` | | none |
| `--username <name>` | | `bachvn1711` |
| `--remote-tag <tag-or-URI>` | | none |
| `--skip-login` | | false |

Build locally with Podman:

```powershell
vssctl pipeline `
  --version 6.0 `
  --tag localhost/kuksa-databroker:vss-6.0-custom `
  --engine podman
```

Build and publish:

```powershell
$env:GHCR_TOKEN = "YOUR_GITHUB_PAT"
vssctl pipeline `
  --version 6.0 `
  --tag localhost/kuksa-databroker:vss-6.0-custom `
  --engine podman `
  --publish `
  --username YOUR_GITHUB_USERNAME `
  --remote-tag vss-6.0-custom
Remove-Item Env:GHCR_TOKEN
```

### `vssctl browse`

Open the interactive Textual terminal UI.

```powershell
vssctl browse
vssctl browse --source base
vssctl browse --source custom
vssctl browse --source merged
```

`--source` accepts `base`, `custom`, or `merged` and defaults to `merged`.
This command requires an interactive terminal.

### `vssctl dashboard`

Start the read-only Flask web dashboard.

| Option | Default | Meaning |
|---|---|---|
| `--host <host>` | `127.0.0.1` | Bind interface. |
| `--port <1..65535>` | `5555` | TCP port. |
| `--catalog-dir <dir>` | built-in catalog location | Team YAML catalog directory. |
| `--debug` / `--no-debug` | `--no-debug` | Toggle Flask debug mode. |

Examples:

```powershell
vssctl dashboard
vssctl dashboard --host 0.0.0.0 --port 8080
vssctl dashboard --catalog-dir workspace\catalog --debug
```

Open `http://127.0.0.1:5555` for the default invocation. Stop the server with
`Ctrl+C`. Do not expose debug mode on an untrusted network.

### `vssctl completion`

Generate a completion script for Bash, Zsh, or Fish:

```bash
vssctl completion bash > ~/.vssctl-completion.bash
source ~/.vssctl-completion.bash

vssctl completion zsh > ~/.vssctl-completion.zsh
vssctl completion fish > ~/.config/fish/completions/vssctl.fish
```

Typer also provides completion for the current shell:

```powershell
vssctl --show-completion
vssctl --install-completion
```

## 7. End-to-End Podman Workflow

The following sequence starts with a custom signal and ends with a running
Databroker.

### Step 1: activate the environment

```powershell
.\.venv_win\Scripts\Activate.ps1
vssctl --help
```

### Step 2: add and inspect a signal

```powershell
vssctl signal add
vssctl signal list
vssctl signal search Attention
```

### Step 3: validate and generate VSS 6.0

```powershell
vssctl validate
vssctl generate --version 6.0
Test-Path workspace\generated\json_tree\vss_release_6.0.json
```

### Step 4: build the custom image

```powershell
podman machine start
vssctl build `
  -f workspace\generated\json_tree\vss_release_6.0.json `
  -t localhost/kuksa-databroker:vss-6.0-custom `
  --engine podman
```

### Step 5: run the Databroker

```powershell
podman run --rm -d `
  --name custom-kuksa `
  -p 55555:55555 `
  localhost/kuksa-databroker:vss-6.0-custom `
  --insecure
```

Check startup state and logs:

```powershell
podman ps
podman logs custom-kuksa
```

Stop it when finished:

```powershell
podman stop custom-kuksa
```

## 8. Test a Custom Signal with KUKSA Client

### Python KUKSA client on the host

Install the client in the active virtual environment:

```powershell
python -m pip install kuksa-client
kuksa-client grpc://127.0.0.1:55555
```

In the interactive client, replace the example path with the signal you added:

```text
getValue Vehicle.ADAS.DriverMonitoring.AttentionLevel
setValue Vehicle.ADAS.DriverMonitoring.AttentionLevel 80
getValue Vehicle.ADAS.DriverMonitoring.AttentionLevel
quit
```

Use `setValue` only for a signal accepted as writable by the API. If it is a
read-only sensor and the client rejects `setValue`, feed it through a provider
API or use the Databroker CLI `publish` command.

### Databroker CLI in Podman

Run the official CLI container on the same Podman network as the broker:

```powershell
podman network create kuksa-net
podman stop custom-kuksa
podman run --rm -d `
  --name custom-kuksa `
  --network kuksa-net `
  -p 55555:55555 `
  localhost/kuksa-databroker:vss-6.0-custom `
  --insecure
podman run --rm -it `
  --network kuksa-net `
  ghcr.io/eclipse-kuksa/kuksa-databroker-cli:main `
  --server http://custom-kuksa:55555
```

In the Databroker CLI:

```text
get Vehicle.ADAS.DriverMonitoring.AttentionLevel
feed Vehicle.ADAS.DriverMonitoring.AttentionLevel 80
get Vehicle.ADAS.DriverMonitoring.AttentionLevel
quit
```

## 9. Configuration File

Pass a file explicitly with `--config`, or place `.vssctl.yaml` in the project
root or user home directory:

```yaml
workspace:
  databroker_path: workspace/databroker
  output_dir: workspace/output

defaults:
  engine: auto
  ghcr_org: bachvn1711
  vss_version: "6.0"
```

Current implementation notes:

- `workspace.databroker_path` is used as the default build workspace;
- `defaults.vss_version` can affect generation when configured;
- `defaults.ghcr_org` is used by the web dashboard;
- `workspace.output_dir` and `defaults.engine` are parsed but not consistently
  used by every CLI command yet, so use explicit command options when behavior
  must be deterministic.

## 10. Troubleshooting


### `ModuleNotFoundError: No module named 'textual'` or `flask`

Activate the intended environment and reinstall runtime requirements:

```powershell
.\.venv_win\Scripts\Activate.ps1
python -m pip install -r requirements.txt
python -m pip install -e .
python -m pip check
```

### Databroker workspace root not found

Check for `Cargo.toml`:

```powershell
Test-Path workspace\databroker\kuksa-databroker\Cargo.toml
```

If false:

```powershell
git clone https://github.com/eclipse-kuksa/kuksa-databroker.git workspace\databroker\kuksa-databroker
```

Or point the command to an existing clone:

```powershell
vssctl build --databroker-dir C:\src\kuksa-databroker --engine podman
```

### Podman tries to pull a local image from Docker Hub

The image was not built under the name passed to `podman run`. List local
images and use an explicit `localhost/` tag:

```powershell
podman images
podman tag kuksa-databroker:vss-6.0-custom localhost/kuksa-databroker:vss-6.0-custom
podman run --rm localhost/kuksa-databroker:vss-6.0-custom --insecure
```

### Podman command appears stuck

Inspect it from a second PowerShell terminal:

```powershell
podman ps -a
podman logs custom-kuksa
podman machine list
podman info
```

Container builds can spend a long time compiling Rust dependencies on the first
run. Keep the build log visible; use `--no-cache` only when a clean rebuild is
actually required.

### Generated files do not appear in Git changes

They are ignored intentionally. Inspect them without staging them:

```powershell
git status --ignored --short workspace\generated
Get-ChildItem workspace\generated\json_tree
git check-ignore -v workspace\generated\json_tree\vss_release_6.0.json
```

To compare two local generated runs, copy the first output outside the ignored
directory and compare it after regenerating:

```powershell
Copy-Item workspace\generated\json_tree\vss_release_6.0.json $env:TEMP\vss_release_6.0.before.json
vssctl generate --version 6.0
Compare-Object `
  (Get-Content $env:TEMP\vss_release_6.0.before.json) `
  (Get-Content workspace\generated\json_tree\vss_release_6.0.json)
```


## 11. CI Release Workflow

`.github/workflows/release.yml` installs the package, runs tests, validates the
catalog, generates VSS 6.0 JSON, builds a Databroker image, and can attach the
generated files from `workspace/generated/json_tree/` to a tagged release.

Before relying on CI, reproduce the core checks locally:

```powershell
python -m pytest
vssctl validate
vssctl generate --version 6.0
```
